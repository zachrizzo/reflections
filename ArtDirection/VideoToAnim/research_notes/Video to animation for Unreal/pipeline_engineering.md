# Engineering a video-to-animation batch pipeline for Unreal Engine 5.9 (Windows 11, RTX 5080)

Research date: 2026-11-21. All sources were fetched on that date ("accessed 2026-11-21") unless another date is given.
Legend: VERIFIED = read on the cited primary page (repo README/docs, paper, Epic docs, forum thread) on 2026-11-21. VERIFIED-anecdotal = a forum or issue comment that is real but is one user's report. UNVERIFIED = I could not confirm it from a primary source; it is labelled as such and kept out of Cited Findings where possible. Effort numbers are my estimates, with assumptions stated. Page contents were extracted through a fetch tool that summarises pages, so exact wording and numbers should be re-checked on the page before the owner relies on them for a decision.

Headline findings the report writer should not miss:
1. NVIDIA GEM-X (Apache-2.0 code, separate model licence) reconstructs world-grounded motion from video directly on the SOMA skeleton, the same family Kimodo emits. It is the only candidate that skips SMPL entirely. It ships no BVH/NPZ exporter, so a glue step is needed (the biggest single integration unknown).
2. Kimodo already ships the pieces on the output side: `kimodo.exports.bvh.motion_to_bvh`, `kimodo_convert` (Kimodo NPZ <-> SOMA BVH), and a foot-skate `post_process_motion`. SOMA-X ships `tools.smpl2soma` and `tools.mhr2soma` for SMPL and SAM 3D Body (MHR) input.
3. Epic released a free, experimental, Windows-only "MetaHuman Animator Markerless Motion Capture" plugin for UE 5.8+ (June 2026). It produces body+hands (and optionally face) animation from one camera, drives the MetaHuman skeleton directly, and claims Python/Blueprint automation. It is a cheap baseline to test first.
4. On this machine (local read-only check) the GPU is an RTX 5080 with 16,303 MiB, of which 13,228 MiB was already in use at the time of the check, and `py -0` lists only Python 3.14. Most research repos want Python 3.10 to 3.12, so a version-managed environment (uv/conda) is mandatory, and GPU jobs and the Unreal editor cannot share the card.

## 1. Windows / Blackwell feasibility of the leading open models

### Takeaway
GEM-X (NVIDIA, torch 2.10+, pure wheels plus ONNX detectors, built on SOMA-X which documents Windows) is the most plausible native-Windows RTX 5080 candidate and also the only one that natively emits SOMA. GVHMR, WHAM, TRAM, PromptHMR and CameraHMR are Linux-first research code with pinned pre-Blackwell torch versions and compiled extensions (DPVO, DROID-SLAM, pytorch3d); they are feasible on WSL2 or with patches, but cost days, not hours. The editor and any GPU job cannot run together on a 16 GB card.

### Cited Findings
- Blackwell (sm_120) needs CUDA 12.8 builds: PyTorch 2.7 (blog dated 2025-05-15) introduced Blackwell support and cu128 wheels, install command `pip install torch==2.7.0 --index-url https://download.pytorch.org/whl/cu128`; the blog states wheels for "Linux x86 and arm64", so Windows cu128 availability is not stated there. VERIFIED. [PyTorch 2.7 blog](https://pytorch.org/blog/pytorch-2-7/)
- Windows RTX 50-series users in 2025 were told to use nightly or cu128 builds, and report sm_120 "not compatible" errors on older stable builds. VERIFIED-anecdotal. [NVIDIA forum](https://forums.developer.nvidia.com/t/rtx-5090-not-working-with-pytorch-and-stable-diffusion-sm-120-unsupported/338015), [PyTorch forum, RTX 5080 Windows](https://discuss.pytorch.org/t/pytorch-cannot-detect-rtx-5080-requires-cuda-12-8-nightly-build-fails-to-install-correctly-on-windows/223957)
- Local machine (read-only `nvidia-smi` and `py -0`, 2026-11-21): NVIDIA GeForce RTX 5080, driver 610.88, 16,303 MiB total, 13,228 MiB used at the moment of the check; only Python 3.14 is registered with the py launcher. VERIFIED (local check, no URL).
- **GEM-X** (NVlabs): Python 3.10+, PyTorch 2.10+, install `pip install -e '.[video,hand]'`; FFmpeg required; person detector is YOLOX via ONNX Runtime and the hand detector is RT-DETR via ONNX, `--detector-device` defaults to CPU; installs SOMA runtime 0.3.3. Mesh rendering is stated for Linux x86-64 with Open3D 0.19.0 only (rendering is optional, inference does not need Open3D). The README and INSTALL.md do not mention Windows or WSL, and give no VRAM or fps figure. VERIFIED. [GEM-X README](https://github.com/NVlabs/GEM-X), [INSTALL.md](https://github.com/NVlabs/GEM-X/blob/main/docs/INSTALL.md)

VERIFIED. [SOMA-X installation.md](https://github.com/NVlabs/SOMA-X/blob/main/docs/installation.md), [NVIDIA Warp](https://github.com/NVIDIA/warp)

[INSTALL.md](https://github.com/zju3dv/GVHMR/blob/main/docs/INSTALL.md), [README](https://github.com/zju3dv/GVHMR)

- **SAM 3D Body** (Meta): single-image full-body HMR producing Momentum Human Rig (MHR) pose; SAM License; demo defaults to ViTDet + MoGe2 FOV model; checkpoint access requires a request; no video mode. VERIFIED. [SAM 3D Body README](https://github.com/facebookresearch/sam-3d-body)
- **WSL2**: NVIDIA's CUDA-on-WSL guide: needs WSL 2 and Windows 11 (or Win10 21H2+), install only the Windows driver (never a Linux display driver in WSL), limitations include no full Unified Memory, limited pinned memory, limited `nvidia-smi`, Docker via NVIDIA Container Toolkit with `--gpus all` only. VERIFIED. [CUDA on WSL User Guide](https://docs.nvidia.com/cuda/wsl-user-guide/index.html)

- Kimodo (what the owner already runs): full local generation needs about 17 GB VRAM, mostly the text encoder; `TEXT_ENCODER_DEVICE=cpu` brings it under 3 GB; tested mainly on RTX 3090/4090/A100; "developed on Linux", Windows "should work especially if using Docker". Install is Python 3.10+, torch 2.0+. VERIFIED. VERIFIED-anecdotal (search summary of community threads). [SageAttention #262](https://github.com/thu-ml/SageAttention/issues/262), [GVHMR #23](https://github.com/zju3dv/GVHMR/issues/23)

### Inferences
- PromptHMR's two supported torch builds (2.4/cu121, 2.6/cu126) and CameraHMR's torch 2.0/cu118 all predate the torch 2.7 / cu128 release that added Blackwell support, and the precompiled `--world-video` wheels are tied to those versions. So on an RTX 5080 these would need a rebuild or a torch upgrade that the authors have not validated. (Inference from the PyTorch 2.7 blog.)
- GEM-X requiring torch 2.10+ means any default cu128/cu130 wheel already contains sm_120 kernels, so Blackwell is likely a non-issue for GEM-X itself. Not confirmed by any Windows report.
- GVHMR with `-s` (static camera) avoids DPVO/SimpleVO entirely; combined with no pytorch3d in INSTALL.md, a "static camera only" GVHMR install may avoid the worst Windows build steps. Whether `requirements.txt` pulls pytorch3d was not visible in any fetched page (UNVERIFIED).
- Practical route on this machine: (1) try GEM-X natively on Windows in a uv-managed Python 3.12 venv with torch cu128; (2) if any dependency fights back, use WSL2 Ubuntu (plain venv, not Docker) with the Windows driver; (3) treat GVHMR/WHAM/TRAM as WSL2-only. WSL2 on Blackwell works in some reports and fails in others, so verify with a real tensor op, not just `nvidia-smi`.
- VRAM coexistence: with 13.2 GB used at the time of the check (the owner's notes put the editor at about 11 GB), only about 3 GB is free. GEM-X and GVHMR inference (8 to 15 GB reported for GVHMR) will not fit next to the editor; schedule video jobs when the editor is closed, or run detector/ViTPose stages on CPU via ONNX (GEM-X default detector device is CPU). WSL2 shares the same physical GPU, so it does not help here.

### Gaps
- No primary source gives GEM-X VRAM or fps. Must be measured.
- No confirmed report of GEM-X running natively on Windows; none of the GEM-X docs say Windows is supported or unsupported.
- No confirmed Blackwell + GVHMR success beyond one issue comment; no primary info on WHAM/TRAM on sm_120.
- Models I did not research: TokenHMR, SLAHMR, CoMotion, Human3R, VIMO and other 2025-2026 entrants; the other researcher profiles individual models.

## 2. Input requirements and video prep

### Takeaway
Plan for one person, full body in frame, a locked-off camera (static mode is the best-supported and cheapest path), constant 30 fps, pinhole (undistorted) footage, and clips of at most 60 seconds for GEM-X. Use Apache/MIT detectors/trackers (YOLOX, RT-DETR, ViTPose, ByteTrack, RTMPose via rtmlib) rather than YOLOv8, which GVHMR's weights use.

### Cited Findings
- GEM-X video handling: input normalised to 30 fps with FFmpeg; `--start`/`--duration` in seconds; clips up to 60 s, longer inputs need an explicit duration; post-process needs one complete unpadded sequence of at least 2 frames with continuous 30 Hz timestamps; `--camera-mode static|vipe` (moving camera needs ViPE); ViPE requires pinhole video, so wide-angle/fisheye footage must be rectified first; hand pipeline accepts pinhole and fisheye camera adapters. VERIFIED. [GEM-X DEMO.md](https://github.com/NVlabs/GEM-X/blob/main/docs/DEMO.md), [VIPE_CAMERA.md](https://github.com/NVlabs/GEM-X/blob/main/docs/VIPE_CAMERA.md)
- GEM-X person selection: Body Motion tracks one primary person, the one with the largest cumulative detected area; pose-video uses ByteTrack and also picks the largest cumulative box; boxes with distinct `track_id` can be supplied for several people; internal tracking gaps are interpolated and endpoint boxes held; detector `weights/yolox_humanart.onnx`; 2D keypoints from a ViTPose-family checkpoint (`vitpose77-dinov3-huge-metrosim-256x192-v1`). Output width must be even and at least 64 px. VERIFIED. [GEM-X DEMO.md](https://github.com/NVlabs/GEM-X/blob/main/docs/DEMO.md)
- GEM-X documented failure conditions (open issue titles): tracking fails when the person is partially out of frame (#11); tracking failure and limb swapping when foot elevation exceeds hip height (#26); unstable motion when hands are static and feet move vigorously (#27); incorrect hip rotation when body movement is minimal (#25); static-motion quality (#13). VERIFIED (titles only; bodies not read). [GEM-X issues](https://github.com/NVlabs/GEM-X/issues)
- GVHMR input options: `tools/demo/demo.py --video=...`, `demo_folder.py -f <in> -d <out>` for batch folders, `-s` for known-static camera (otherwise visual odometry estimates it), `f_mm` sets full-frame focal length in mm; checkpoints include `yolov8x.pt` for person detection. VERIFIED. [GVHMR README](https://github.com/zju3dv/GVHMR), [INSTALL.md](https://github.com/zju3dv/GVHMR/blob/main/docs/INSTALL.md)
- TRAM and PromptHMR expose `--static_camera`; PromptHMR also has `--gravity_align` (single image) and is described as multi-human world-coordinate video; WHAM defaults to SLAM with `--calib` for intrinsics. VERIFIED. [TRAM](https://github.com/yufu-wang/tram), [PromptHMR](https://github.com/yufu-wang/PromptHMR), [WHAM](https://github.com/yohanshin/WHAM)
- Permissive detector/pose stack in one wheel-friendly library: `rtmlib` (Apache-2.0) runs YOLOX, RTMDet (hand), RF-DETR detectors and RTMPose/RTMW/DWPose/ViTPose pose models on onnxruntime without mmcv/mmpose/mmdet; `PoseTracker` runs detection every N frames (`det_frequency`) and tracks in between; GPU via `onnxruntime-gpu`; README warns that weights trained on non-commercial datasets such as COCO-WholeBody carry separate considerations. Windows is implied, not stated. VERIFIED. [rtmlib README](https://github.com/Tau-J/rtmlib)
- GEM-X already uses permissive-licence-class components for detection/tracking: YOLOX (ONNX), RT-DETR (hand detector), ByteTrack, ViTPose-family. The code is Apache-2.0 while weights stay under their own terms (NVIDIA Open Model License for the model). VERIFIED (component names/code licence); licences of each component were not individually read. [GEM-X README](https://github.com/NVlabs/GEM-X)
- Epic's MetaHuman Animator markerless plugin (for comparison) reportedly failed on 29.97 and 30 fps image sequences until the capture-data frame rate was set correctly (a user report); this is a reminder to force a constant frame rate before ingest. VERIFIED-anecdotal. [Epic forum thread](https://forums.unrealengine.com/t/epic-games-metahuman-animator-markerless-motion-capture-plugin/2729293)
- Per the user's brief, YOLO (Ultralytics) is AGPL; the only direct evidence I fetched is that GVHMR's required weights include `yolov8x.pt`. The AGPL licence itself was not independently fetched. UNVERIFIED (licence) / VERIFIED (file name). [GVHMR INSTALL.md](https://github.com/zju3dv/GVHMR/blob/main/docs/INSTALL.md)

### Inferences
- Own-filmed footage checklist (my synthesis; each item is UNVERIFIED engineering advice, derived from the failure-mode issues above and general monocular HMR behaviour): tripod, lock exposure, 1080p or higher at 30 fps constant frame rate (or 60 fps downsampled with correct timestamps), subject fills 60 to 80 percent of frame height with head to toe visible for the whole clip, no one else crossing the frame, plain contrasting background, fitted clothing (loose skirts or capes confuse leg tracking), avoid heavy motion blur (shutter about 1/120 s or faster), flat ground visible, include a short A/T-pose at the start, no zoom, shoot rectilinear (not wide-angle or action-cam fisheye).
- Static camera (locked tripod) lets you skip visual odometry (`-s` / `--camera-mode static` / `--static_camera`), which removes DPVO/DROID-SLAM/ViPE, the three hardest builds on Windows. This is the cheapest and most robust path for own-filmed reference, so the owner should film static by default.
- For multiple people in frame, GEM-X's "largest cumulative area" heuristic is brittle; deterministic selection means pre-cropping to one actor (ffmpeg crop or a ByteTrack ID chosen on a contact sheet) and passing that as the source clip.
- Trimming: GEM-X's 60 s cap and 10 s Kimodo-style clip lengths suggest cutting source takes into 5 to 20 s action clips by script (ffmpeg `-ss/-t`, re-encode to constant 30 fps) before pose estimation.

### Gaps
- No source on lens-distortion tolerance beyond GEM-X/ViPE's "pinhole only"; no data on how much rectification matters for GVHMR/WHAM.
- No quantitative guidance on minimum resolution, subject-height-in-frame, or motion blur for any model; the repos do not document it.
- Detector/tracker licences (YOLOX, RT-DETR, ByteTrack, ViTPose, RTMDet/RTMPose) were not individually fetched; that belongs to the licence researcher.

## 3. Output conversion (SMPL/SOMA/other to BVH/FBX and to a UE skeleton)

### Takeaway
The cleanest route to the owner's existing SOMA retargeter is GEM-X (native SOMA) or SMPL-family models routed through SOMA-X `tools.smpl2soma`, then Kimodo's `motion_to_bvh` / `kimodo_convert`. The glue code between GEM-X `.pt` files (or `smpl2soma` NPZ) and Kimodo's `local_rot_mats` + `root_positions` layout is not documented anywhere I could find, and is the main schedule risk. GMR, SOMA Retargeter and ProtoMotions retarget to robots, not MetaHuman.

### Cited Findings
- **Kimodo motion format** (all models): NPZ with `posed_joints [T,J,3]`, `global_rot_mats [T,J,3,3]`, `local_rot_mats [T,J,3,3]`, `foot_contacts [T,4]` (left heel, left toe, right heel, right toe), `smooth_root_pos [T,3]`, `root_positions [T,3]`, `global_root_heading [T,2]`; J = 77 for SOMA (`somaskel77`; the model runs internally on `somaskel30` and expands on export), 34 for G1, 22 for SMPL-X. NPZ zero pose is Kimodo's own standard T-pose. VERIFIED. [Kimodo output formats](https://research.nvidia.com/labs/sil/projects/kimodo/docs/user_guide/output_formats.html), [Kimodo skeleton docs](https://research.nvidia.com/labs/sil/projects/kimodo/docs/key_concepts/skeleton.html)
- **Kimodo BVH export (SOMA only)**: `--bvh` on CLI generation; hierarchy `somaskel77`; root translation plus per-joint local rotations; rest pose defaults to the BONES-SEED convention, `--bvh_standard_tpose` switches to a standard T-pose; plain-text BVH, units scaled to centimetres; requires the `bvhio` package. VERIFIED. [Kimodo output formats](https://research.nvidia.com/labs/sil/projects/kimodo/docs/user_guide/output_formats.html), [kimodo.exports.bvh source](https://research.nvidia.com/labs/sil/projects/kimodo/docs/_modules/kimodo/exports/bvh.html)
- **`kimodo_convert INPUT OUTPUT`** converts Kimodo NPZ <-> SOMA BVH (accepts 77 joints or 30 expanded to 77), AMASS NPZ (SMPL-X, 22 joints) <-> Kimodo NPZ, G1 CSV <-> Kimodo NPZ; always writes 30 Hz (resamples with linear/slerp and recomputes velocities, contacts, heading via FK); BVH import only guaranteed for Kimodo-exported BVHs (a `Root` wrapper with SOMA77 joint names) and BONES-SEED BVHs, other hierarchies "may fail". VERIFIED. [Kimodo motion convert](https://research.nvidia.com/labs/sil/projects/kimodo/docs/user_guide/motion_convert.html)
- **Kimodo Python API**: `kimodo.exports.bvh.motion_to_bvh(local_rot_mats, root_positions, *, skeleton, fps, standard_tpose=False)`, `save_motion_bvh(path, ...)`, `bvh_to_kimodo_motion(path, skeleton=None, ...)`; `kimodo.skeleton.bvh.parse_bvh_motion`; `SOMASkeleton77().to_standard_tpose(local_rot_mats)` remaps the BONES-SEED rest pose to the standard T-pose; `KimodoMotionRep(skeleton, fps).canonicalize/inverse` rebuilds the full motion dict (`foot_contacts`, `smooth_root_pos`, etc.). VERIFIED. [Kimodo exports API](https://research.nvidia.com/labs/sil/projects/kimodo/docs/api_reference/exports.html), [Kimodo seed dataset page](https://research.nvidia.com/labs/sil/projects/kimodo/docs/user_guide/seed_dataset.html)
- Kimodo docs call the SMPL-X skeleton option (22 body joints, AMASS-style exports) "not recommended because of severe retargeting artifacts" and Kimodo-SMPLX weights use the NVIDIA R&D Model License; most Kimodo-SOMA/G1 models use the NVIDIA Open Model License; code is Apache-2.0. VERIFIED. [Kimodo skeleton docs](https://research.nvidia.com/labs/sil/projects/kimodo/docs/key_concepts/skeleton.html), [Kimodo README](https://github.com/nv-tlabs/kimodo)
- **SOMA-X conversion tools** (Apache-2.0): `python -m tools.smpl2soma` converts an SMPL animation to SOMA via `PoseInversion` (analytical fitting default, `--autograd-iters` for differentiable FK refinement, `--output-npz`); `tools.mhr2soma` converts MHR parquet data, including SAM 3D Body outputs, to SOMA with `--smooth` RTS smoothing presets; `tools.convert_amass_to_soma` converts one AMASS sequence or a tree to SOMA NPZ; `tools.convert_identity_backend` converts identity between MHR, Anny, SMPL, SMPL-H, SMPL-X; SMPL/SMPL-X/MANO files must be user-supplied under their own licences. SOMA-X documents USD/NPZ I/O and no BVH or FBX exporter. VERIFIED. [SOMA-X tools.md](https://github.com/NVlabs/SOMA-X/blob/main/docs/tools.md), [SOMA-X README](https://github.com/NVlabs/SOMA-X)
- **GEM-X output**: `.pt` dictionaries (`gem_body_video_predictions_v1`, `gem_motion_predictions_v1`) with `pred_soma_params_incam` and `pred_soma_params_global` plus static-contact logits (six contact logits: ankles, feet, wrists); `gem-render` produces `overlay.mp4`/`world.mp4`; the docs do not state the rotation representation, joint count of the output, tensor shapes, or any BVH/NPZ/FBX/USD export. The body-pose model predicts 76 joint-local rotations plus 128 identity coefficients; GEM-X lists the SOMA Retargeter as its robot (G1) path. VERIFIED. [GEM-X DEMO.md](https://github.com/NVlabs/GEM-X/blob/main/docs/DEMO.md), [MODEL_OVERVIEW.md](https://github.com/NVlabs/GEM-X/blob/main/docs/MODEL_OVERVIEW.md), [GEM-X README](https://github.com/NVlabs/GEM-X)
- **NVIDIA SOMA Retargeter** (`NVIDIA/soma-retargeter`, Apache-2.0 code, beta): input is SOMA-base-skeleton BVH only (other rigs "may load incorrectly or fail"); output is robot CSV (root pose plus actuated joints); bundled robots Unitree G1/H2, Booster T1, AgiBot X2 Ultra/A3T3; includes foot-plant correction and joint limits; no BVH output, no human-skeleton retargeting; sample motions under the NVIDIA Sample Data Evaluation License; Windows not explicitly stated (docs mention PowerShell). VERIFIED. [soma-retargeter README](https://github.com/NVIDIA/soma-retargeter), [NVIDIA blog](https://developer.nvidia.com/blog/?p=125128)
- **GMR (General Motion Retargeting)** (MIT): accepts SMPL-X/AMASS, BVH (LAFAN1, Nokov), FBX (OptiTrack), Xsens, and GVHMR output (`scripts/gvhmr_to_robot.py`); targets 19 humanoid robots; saves `.pkl` (CSV via `batch_gmr_pkl_to_csv.py`), no BVH output; tested on Ubuntu 22.04/20.04; Kimodo documents Kimodo-SMPLX AMASS NPZ -> GMR as an example. VERIFIED. [GMR README](https://github.com/YanjieZe/GMR), [Kimodo README](https://github.com/nv-tlabs/kimodo)
- **ProtoMotions** consumes Kimodo SOMA NPZ (`local_rot_mats [T,77,3,3]`, `posed_joints [T,77,3]`, optional `foot_contacts`) and SOMA BVH (Y-up, 120 fps, cm) through `convert_soma23_npz_to_proto.py` / `convert_soma23_bvh_to_proto.py`; all converters compute heuristic ground-contact labels from height/velocity thresholds (values not given); it reduces 77 joints to 23 actuated bodies. VERIFIED. [ProtoMotions Kimodo preparation](https://nvlabs.github.io/ProtoMotions/getting_started/kimodo_preparation.html), [ProtoMotions SEED BVH preparation](https://nvlabs.github.io/ProtoMotions/getting_started/seed_bvh_preparation.html)
- **GVHMR result file**: users export `smpl_params_global` (`body_pose`, `global_orient`, `transl`, `betas`) from `hmr4d_results` to a pickle so Blender can read it without PyTorch; a Blender 4.2 file plus an SMPL FBX (SMPL_maya) retargets it; the free add-on `ceb_hubmocap` combines GVHMR or PromptHMR body motion with HaMeR fingers and a Mixamo retarget option; `sam-3d-body-blender` also exists (untested by that author). Reported pitfalls: root pelvis not moving (wrong `demo.py` edit), numpy/Python-version conflicts, HaMeR hand jitter. VERIFIED-anecdotal. [GVHMR #10](https://github.com/zju3dv/GVHMR/issues/10)
- **Meshcapade SMPL Blender add-on**: add-on code GPL-3.0; loading `.npz` AMASS animation and adding SMPL-X bodies are licensed-user features; repository marked discontinued with a successor (`smplx_blender_addon`); says nothing about game engines. VERIFIED. [SMPL_blender_addon](https://github.com/Meshcapade/SMPL_blender_addon)
- **SAM-3D-Body -> MHR -> Manny FBX** (community portfolio pipeline): scripts `sam3d_track_to_smplx.py`, `mhr_track_to_manny_fbx.py` run via `blender -b -P`; Manny bone-name mapping, `global_delta` for root/pelvis and `relative_delta` for spine/extremities, clavicle weight blending, flags `--max_hand_deg`, `--no_twist`, `--apply_global_rot`; author notes multiple conversion steps compound errors and twist bones can give messy animation; hands snap without clamping; output keeps Manny hierarchy, -Y forward, Z-up, 30 fps. Licences not stated. VERIFIED (single portfolio page). [Video-to-Motion Capture Pipeline](https://timothybunker.github.io/TimBunkerPortfolio/projects/video-mocap-pipeline/)
- **Motion2MixamoRig** (Apache-2.0): GVHMR -> SMPL-X -> Mixamo FBX retarget -> skinned `.glb`; separate terms for SMPL-X, Mixamo assets and weights; single-person clips; the third-party summary says about 5 GB first-run download and 8 to 15 minutes for a 30 s clip and says it runs on CPU (internally inconsistent page, treat as UNVERIFIED). [alphasignal summary](https://alphasignal.ai/news/motion2mixamorig-turns-a-phone-video-into-a-rigged-3d-animation)
- PromptHMR video outputs are `.mcs` and `.glb` (and `results.pkl`); GLB imports into Blender; no BVH/FBX exporter. TRAM, WHAM and CameraHMR READMEs mention no Blender/FBX/BVH export. VERIFIED. [PromptHMR README](https://github.com/yufu-wang/PromptHMR)

### Inferences
- Candidate routes into the owner's SOMA retargeter, ranked by expected effort (estimates, not measurements):
  1. GEM-X -> custom glue -> Kimodo NPZ/BVH. Glue = run SOMA FK from `pred_soma_params_global` to get `local_rot_mats [T,77,3,3]` and root positions, then `motion_to_bvh` or `kimodo_convert`. Open question: whether GEM-X (py-soma-x 0.3.3) and Kimodo's `somaskel77` share the same rest pose and rotation convention. Kimodo's `soma_layer_skin.py` is described as a SOMA layer driven by identity parameters, so FK through the SOMA layer is plausible, but no document states the conversion. Budget 1 to 3 days.
  2. SMPL-family model (GVHMR/WHAM/TRAM/PromptHMR) -> `tools.smpl2soma --output-npz` -> glue to Kimodo layout -> `motion_to_bvh`. Same glue risk (the NPZ keys of `smpl2soma` were not documented on the pages I read), plus SMPL licence and a pose-inversion fit that adds its own error.
  3. SAM 3D Body (MHR) -> `tools.mhr2soma --smooth`; single-image model so jitter and root-trajectory handling are on you; SAM licence.
  4. AMASS/SMPL-X -> `kimodo_convert` gives a 22-joint SMPL-X Kimodo NPZ, not SOMA, so it does not reach the SOMA retargeter and Kimodo itself warns about retargeting artifacts on that skeleton.
- Robot-oriented retargeters (GMR, SOMA Retargeter, ProtoMotions) are only useful here for their cleanup ideas (foot-plant correction, contact heuristics); none outputs a human skeleton.
- A SMPL -> Blender -> Manny/MetaHuman path (ceb_hubmocap, Tim Bunker's scripts, Motion2MixamoRig) already exists in community form and could be a fallback if SOMA glue stalls; it has its own error compounding and licence gates on SMPL data.
- Whether the owner's current retargeter takes Kimodo NPZ, SOMA BVH or something else was not inspected (read-only constraint), so which exporter to target (NPZ via glue, or BVH via `motion_to_bvh`) must be confirmed locally.

## 4. Cleanup stage

### Takeaway
Contact and skate cleanup is partly free: GEM-X has a built-in contact/IK postprocess and Kimodo ships `post_process_motion` for the SOMA skeleton taking per-frame foot contacts. Jitter filtering (1 euro filter or RTS/Savitzky-Golay in rotation space), ground alignment, root-motion extraction and loop closing are custom code. Monocular failure modes (heel lift, leg splitting, hip-rotation errors, limb swaps) are documented in GEM-X's own issue tracker and cannot be fully removed by filtering.

### Cited Findings
- **GEM-X `--postprocess`**: uses six ankle/foot/wrist contact logits to adjust world translation and body pose; smooths X/Z and aligns the lowest public joint's Y to the ground even without positive contacts; root orientations, identity, scale, camera-space translation and logits are unchanged; raw values are kept in `raw_predictions` and diagnostics in `postprocessing`; needs one unpadded sequence with continuous 30 Hz timestamps; does not correct camera depth or RGB alignment. VERIFIED. [GEM-X DEMO.md](https://github.com/NVlabs/GEM-X/blob/main/docs/DEMO.md)
- GEM-X benchmark (EMDB-2, Body Motion): W-MPJPE100 267.20 mm, WA-MPJPE100 112.76 mm, RTE 2.45 percent, jitter 34.21, foot sliding 4.22 mm (units as published in the README). VERIFIED. [GEM-X README](https://github.com/NVlabs/GEM-X)
- **Foot-contact outputs in other models**: GVHMR predicts "stationary probabilities for predefined joints" and root velocity, then converts to world using camera rotation (gravity-view coordinates, per-frame, avoiding autoregressive drift); WHAM uses a contact-aware trajectory refinement to counter foot sliding. VERIFIED. [GVHMR project page](https://zju3dv.github.io/gvhmr/), [WHAM abstract](https://arxiv.org/abs/2312.07531)
- **Kimodo `kimodo.postprocess.post_process_motion`**: inputs `local_rot_mats (B,T,J,3,3)`, `root_positions (B,T,3)`, `contacts (B,T,num_contacts)`, `skeleton`, optional constraints, `contact_threshold=0.5`, `root_margin=0.04`; returns corrected `local_rot_mats`, `root_positions`, `posed_joints`, `global_rot_mats`; helper `create_working_rig_from_skeleton(skeleton, above_ground_offset=0.007)`; documented purpose "reduce foot skating"; docs say it works poorly for the G1 skeleton and recommend it when foot contact accuracy matters; the page does not mention SOMA input from external sources or compiled components. VERIFIED. [Kimodo post-processing](https://research.nvidia.com/labs/sil/projects/kimodo/docs/api_reference/post-processing.html), [Kimodo limitations](https://research.nvidia.com/labs/sil/projects/kimodo/docs/key_concepts/limitations.html)
- **SOMA Retargeter** applies foot-plant correction during detected contact intervals, tunable timing/settings, plus joint limits (robot-side, but the idea transfers). VERIFIED. [NVIDIA blog](https://developer.nvidia.com/blog/?p=125128)
- **Classic footskate cleanup**: Kovar, Schreiner and Gleicher (SCA 2002) filter foot projections and stretch the leg to cover residual distance; University of Wisconsin released a C++ solver (BSD-style licence) that takes a list of contact constraints and a motion; UnderPressure (2022, Mourot et al.) uses deep learning to detect foot contacts then performs cleanup. VERIFIED. [Footskate cleanup page](https://research.cs.wisc.edu/graphics/Gallery/kovar.vol/Cleanup), [Footskate Solver](https://research.cs.wisc.edu/graphics/Gallery/FootskateSolver)
- **1 euro filter** (Casiez, Roussel, Vogel, CHI 2012): speed-based low-pass filter; `fcmin` controls slow-speed smoothing (lower = less jitter, more lag), `beta` reduces lag in fast motion; tuning: beta 0, fcmin about 1 Hz, tune fcmin on slow motion then raise beta on fast motion (start 0.001 or 0.0001, scale by 10); implementations in Python, C++, JS and others, and built into Unreal Engine per the author's page. VERIFIED. [1 euro filter](https://gery.casiez.net/1euro/)
- **SOMA-X `tools.mhr2soma --smooth`** offers RTS smoothing presets for converted SAM 3D Body data. VERIFIED. [SOMA-X tools.md](https://github.com/NVlabs/SOMA-X/blob/main/docs/tools.md)
- **ProtoMotions** computes heuristic ground-contact labels from height and velocity thresholds for all imported motions (values not given); tracking policies can use them. This is the existing open reference for the physics-based "refine through RL tracking" route. VERIFIED. [ProtoMotions](https://nvlabs.github.io/ProtoMotions/getting_started/kimodo_preparation.html)
- **Hands**: GEM-X ships a separate hand pose model and an RT-DETR hand detector (`hands.pt` output, SOMA25 hand layout), with hand weights distributed via the EgoHand repository which manages access; `ceb_hubmocap` pairs HaMeR fingers with GVHMR or PromptHMR and notes hand jitter needing smoothing; Tim Bunker's export clamps hand rotation (`--max_hand_deg`) because hands snap. VERIFIED. [GEM-X README](https://github.com/NVlabs/GEM-X), [GVHMR #10](https://github.com/zju3dv/GVHMR/issues/10), [Video-to-Motion Capture Pipeline](https://timothybunker.github.io/TimBunkerPortfolio/projects/video-mocap-pipeline/)
- **Documented monocular failure modes (GEM-X open issues, titles only)**: heel lifts off the ground (#9), leg splitting on the floor (#10), tracking failure when partially out of frame (#11), bad pixel alignment and forward lean (#16), incorrect hip rotation when movement is minimal (#25), limb swapping when a foot rises above hip height (#26), unstable motion when hands are static and feet move vigorously (#27). VERIFIED. [GEM-X issues](https://github.com/NVlabs/GEM-X/issues)
- **Root motion in Unreal**: Animation Sequence properties Enable Root Motion, Force Root Lock, and Root Motion Root Lock (Ref Pose, Anim First Frame, Zero); the Epic page does not cover extracting root motion from a pelvis. The IK Retargeter has a Root Motion Generator op (`RootMotionGeneratorOp`) whose settings include root height source (source root scaled by relative height, or retargeted pelvis motion), "Maintain Offset From Pelvis", "Rotate With Pelvis" and "Snap To Ground" (sets root height to Z=0); a UE 5.5 forum thread asks how to generate root motion from an animation that has none. VERIFIED. [Root Motion docs](https://dev.epicgames.com/documentation/unreal-engine/root-motion-in-unreal-engine), [FIKRetargetRootMotionOpSettings](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/IKRig/FIKRetargetRootMotionOpSettings), [UE 5.5 forum thread](https://forums.unrealengine.com/t/using-ik-retargeter-in-5-5-to-create-root-motion-animations/2434717)

### Inferences
- Foot-skate stack of least effort (my proposal): (1) GEM-X `--postprocess` for coarse contact/ground alignment; (2) after conversion to SOMA local rotations, build `contacts [T,4]` (heel/toe left/right, matching `foot_contacts` layout) from GEM-X contact logits or a velocity/height heuristic, then call Kimodo `post_process_motion`; (3) if residual skate remains, a Kovar-style two-bone leg IK pass in Blender or UE Control Rig. Whether `post_process_motion` behaves on externally produced SOMA data is untested in any source.
- Rotation smoothing should be done on quaternions (hemisphere-continuous, filter then renormalise) or on the SO(3) manifold, not on Euler angles or raw matrices; the 1 euro filter plus a short Savitzky-Golay or RTS pass is the standard combo (UNVERIFIED as a recommendation; no source compared them).
- Root motion plan: take the pelvis ground projection as a root trajectory, fit a gravity-aligned ground plane, normalise height/scale to the MetaHuman, then either (a) keep a `root` bone with baked motion and set Enable Root Motion, or (b) let the IK Retargeter Root Motion Generator op create root motion from pelvis. Drift (accumulating XZ error) and height normalisation are custom problems; no source gives a tested recipe.
- Loop detection for walk/idle cycles is not covered by any source I found. Standard approach: pose-distance matrix over pelvis-relative joint positions and velocities, choose a start/end pair with minimal distance, crossfade the last N frames. UNVERIFIED.
- Mirrored limbs, depth ambiguity, wrist twist and ground penetration: no source gave mitigation specifics for these in my reading; typical mitigations (left/right consistency checks, foot-height clamps, wrist twist redistribution to forearm/twist joints) are my own suggestions (UNVERIFIED). GEM-X's issue list shows leg swaps and heel lift are live problems even in NVIDIA's own model.
- Physics refinement (PHC, ProtoMotions tracking) is a heavy optional step; ProtoMotions can ingest SOMA NPZ directly, which is the only documented SOMA-compatible physics route. PHC itself was not researched. Cost is a whole separate RL training environment (Isaac Lab/Gym), so treat as out of scope for a solo MVP.

### Gaps
- No source quantifies how much `post_process_motion` or GEM-X `--postprocess` reduces skate on real footage.
- No source for loop-closing algorithms, ML-based cleanup tools (for example commercial/learned denoisers), PHC, or hand-vs-body retiming specifics.
- Head/neck/eye handling: the SOMA 77 skeleton contains face/toe-end leaf joints (ProtoMotions drops them as unactuated), but I found no statement of what GEM-X predicts for face joints or eyes beyond the "body, hands and face" summary of the README in search results.

## 5. Unreal-side steps (import, retarget, root motion, compression)

### Takeaway
Everything needed is scriptable from Python in the editor (`UnrealEditor-Cmd` or the running editor): FBX animation import onto an existing skeleton, `IKRetargetBatchOperation.duplicate_and_retarget`, IK Retargeter edits through `IKRetargeterController`. Known sharp edges: Python import settings need `automated_import_should_detect_type=False` to avoid accidental SkeletalMeshes, Interchange vs legacy FBX importer quirks, no destination-path parameter on some builds of `duplicate_and_retarget`, and in-engine bakes may not get ACL compression.

### Cited Findings
- **IK Retargeter Python API (Epic page, covers UE 5.9)**: get the controller with `unreal.IKRetargeterController.get_controller(rtg)`; `set_ik_rig(RetargetSourceOrTarget.SOURCE|TARGET, rig)`; `auto_map_chains(AutoMapChainType.FUZZY|EXACT|CLEAR, force_remap)`; retarget pose APIs (`create_retarget_pose`, `set_root_offset_in_retarget_pose`, `set_rotation_offset_for_retarget_pose_bone`, `auto_align_all_bones`); global/root/chain settings objects; op stack (`add_retarget_op(unreal.CurveRemapOp|PinBoneOp|RootMotionGeneratorOp)`, enable/reorder); batch call `unreal.IKRetargetBatchOperation.duplicate_and_retarget(assets, source_mesh, target_mesh, retarget_asset, search, replace, prefix, suffix, remap_referenced_assets)`; `None` meshes use the IK Rig meshes. Stated limitations: only the retarget root can carry translation offsets in a retarget pose; "Ideally, the target should match to the pose that the source is in." VERIFIED. [Epic: Python for IK Retargeter assets](https://dev.epicgames.com/documentation/unreal-engine/using-python-to-create-and-edit-ik-retargeter-assets-in-unreal-engine?lang=en-US)
- **Batch retarget caveats (forum)**: no destination parameter in the binding of that user's build (the 5.8 docs list `target_path`, `use_source_path`, `overwrite_existing_files` and a `run_batch_retarget(inputs)` method that the user's build did not expose); workaround is a suffix then `EditorAssetLibrary.rename_asset` to move results; run `help(unreal.IKRetargetBatchOperation.duplicate_and_retarget)` to see your build's signature; empty results usually mean invalid asset paths or a retargeter without a target IK Rig. VERIFIED. [UE forum thread](https://forums.unrealengine.com/t/using-python-to-retarget-animations-to-a-folder/2838372), [Epic API: DuplicateAndRetarget](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/IKRigEditor/UIKRetargetBatchOperation/DuplicateAndRetarget)
- **FBX animation-only import via Python** (community-verified recipe): `AssetImportTask` with `automated=True`, `replace_existing=True`, `save=True`; `FbxImportUI` with `import_mesh=False`, `import_materials=False`, `import_animations=True`, `import_as_skeletal=True`, `skeleton=<loaded USkeleton>`, `mesh_type_to_import=FBXIT_ANIMATION`, and crucially `automated_import_should_detect_type=False` (otherwise a SkeletalMesh is still created); submit with `AssetToolsHelpers.get_asset_tools().import_asset_tasks([task])`. The thread does not cover `anim_sequence_import_data` (uniform scale, sample rate). VERIFIED-anecdotal. [UE forum thread](https://forums.unrealengine.com/t/python-fbx-import-animation-sequence-only/479678)
- **Interchange state** (searches cover 5.4 to 5.8; none found for 5.9): Epic documents Python/Blueprint/C++ editing of import pipelines; reports include missing references on animation import with Python pipelines (5.5.4), FBX animation attributes not imported by Interchange in 5.8.2 with the legacy importer working (`Interchange.FeatureFlags.Import.FBX False`), and legacy helpers like `UEditorEngine::ImportFbxAnimation` not updated to Interchange. VERIFIED-anecdotal. [Epic: importing with Interchange](https://dev.epicgames.com/documentation/unreal-engine/importing-assets-using-interchange-in-unreal-engine), [5.8.2 attributes thread](https://forums.unrealengine.com/t/importing-fbx-animation-attributes-does-not-seem-to-work-with-interchange-5-8-2/2843197), [Automated animation import thread](https://forums.unrealengine.com/t/automated-animation-import/2653211)
- **Root-motion flags**: Enable Root Motion, Force Root Lock, Root Motion Root Lock (Ref Pose / Anim First Frame / Zero) on the Animation Sequence; extraction mode is set by the Animation Blueprint's Root Motion Mode. VERIFIED. [Root Motion docs](https://dev.epicgames.com/documentation/unreal-engine/root-motion-in-unreal-engine)
- **Animation compression**: ACL ships with the engine since UE 5.3 (per forum summary); ACL bone/curve settings assets live under the ACL plugin content; making ACL project default means editing `BoneCompressionSettings` in `Animation.DefaultObjectSettings` (e.g. BaseEngine.ini); Epic advises against much tuning; a forum thread reports that in-engine "Bake to Anim Sequence" results get `DefaultRecorderBoneCompression` rather than ACL. VERIFIED-anecdotal (forum) / VERIFIED (Epic docs page existence). [Epic: ACL](https://dev.epicgames.com/documentation/unreal-engine/animation-compression-library-in-unreal-engine), [forum on baked compression](https://forums.unrealengine.com/t/animating-in-engine-default-bone-compression-settings-use-animation-recorder-instead-of-acl/2654454)

VERIFIED (secondary: press article and forum thread; Epic docs listing seen in search). ### Inferences
- The shortest UE batch script for this pipeline: loop over FBX files; `AssetImportTask` onto `metahuman_base_skel` with the options above; (optionally) `duplicate_and_retarget` if retargeting is done in UE instead of Blender; then set `enable_root_motion` / `force_root_lock` on the new sequences through the AnimSequence Python properties (property names should be confirmed with `dir()` on a loaded sequence; not verified in a source). Since the owner's shared-skeleton fit work already exists, importing onto `metahuman_base_skel` is the target.

- The Epic markerless plugin is worth a 30-minute baseline test on the same clip before building any custom pipeline; it already writes MetaHuman-skeleton AnimSequences and claims Python automation, but it is experimental, quality is unmeasured in any source I read, and I could not verify it against UE 5.9.

## 6. Pipeline sketch, stage-by-stage effort, PoC and scale-up

### Takeaway
Pipeline: video -> prep -> pose estimation (GEM-X first, GVHMR as fallback) -> world-grounded SOMA -> cleanup -> existing SOMA-to-MetaHuman retarget -> FBX -> UE import -> QA metrics -> Animation Sequence. A single-clip proof of concept is a one-day job if the GEM-X-to-SOMA-BVH glue works; a robust batch pipeline is roughly 2 to 4 weeks of solo agent-assisted work (estimates, assumptions below), and monocular quality limits mean human review stays in the loop.

### Cited Findings
- Components with documented interfaces exist for most stages: GEM-X CLI `gem-infer motion-video --camera-mode static|vipe --postprocess` (output `motion.pt`); Kimodo `kimodo_convert` / `motion_to_bvh` / `post_process_motion`; SOMA-X `tools.smpl2soma` / `tools.mhr2soma`; UE `AssetImportTask` + `FbxImportUI`; `IKRetargetBatchOperation`. VERIFIED (see questions 3, 4, 5). [GEM-X](https://github.com/NVlabs/GEM-X), [Kimodo docs](https://research.nvidia.com/labs/sil/projects/kimodo/docs/user_guide/motion_convert.html), [SOMA-X tools](https://github.com/NVlabs/SOMA-X/blob/main/docs/tools.md)
- GEM-X quality indicators on EMDB-2 (jitter 34.21, foot sliding 4.22 mm, WA-MPJPE100 112.76 mm) give a baseline for the QA stage to compare against. VERIFIED. [GEM-X README](https://github.com/NVlabs/GEM-X)
- GVHMR per-frame network time is tiny (280 ms for 1430 frames on RTX 4090); preprocessing (tracking, ViTPose, HMR2 features) is the real time cost and is not benchmarked in any fetched source. VERIFIED. [GVHMR project page](https://zju3dv.github.io/gvhmr/)

### Inferences
Effort estimates (ESTIMATES, not measurements). Assumptions: one developer assisted by an AI coding agent; the owner already has a working Kimodo environment and a SOMA-to-MetaHuman retarget; Blender and UE Python are scriptable; the GPU is free of the editor while jobs run; model weights, HF access and SMPL licences are in hand; Windows-native first with WSL2 fallback. Ranges include one round of debugging; the first number is "goes well", the second "typical friction".

| 7 QA metrics | foot-skate, jitter, ground penetration, limb-swap/flip detector, preview render and report | 1.5 to 3 days | Low |
| 8 Hands/face (optional) | GEM-X hand model or HaMeR; MetaHuman Animator mono video for face | +3 to 6 days | Medium to high |
| Total | MVP batch with review | about 10 to 20 working days (2 to 4 weeks), plus optional stage 8 | |

Rough proof of concept (about one day, ESTIMATE):
1. (1 h) Film or pick a 10 to 15 s, single-person, full-body, tripod clip of a walk or idle; ffmpeg to constant 30 fps.
2. (1 to 2 h) uv venv with Python 3.12, torch cu128, GEM-X `[video]`; download weights (requires the owner to approve downloads and HF/NVIDIA licence terms); close the editor; run `gem-infer motion-video --camera-mode static --postprocess`.
3. (2 to 4 h) Load `motion.pt`; write a script that runs SOMA FK to get `local_rot_mats [T,77,3,3]` and root positions; write with `kimodo.exports.bvh.save_motion_bvh`; check in Kimodo's viewer or Blender. Fallback if the conversion fights back: GVHMR (WSL2, static) -> `tools.smpl2soma` -> same writer.
4. (1 to 2 h) Feed the BVH to the existing SOMA-to-MetaHuman retarget, export FBX, run the UE batch import recipe, play the sequence.
5. (30 min) Baseline comparison on the same clip with Epic's markerless plugin if time permits.
Success criteria: feet planted within a visible tolerance during stance, no mirrored limbs, plausible root path, a loadable `AnimSequence` on `metahuman_base_skel`.

Scale-up cost (ESTIMATES): per-clip human review will dominate. Add roughly 5 to 10 minutes of review per clip (a contact-sheet plus world-view preview); queue management, GPU scheduling around editor sessions, and a QA dashboard add 2 to 4 days. Compute is small relative to review: the GVHMR network is 280 ms per 45 s of footage on a 4090, with preprocessing as the unbenchmarked remainder. Re-shoots are cheaper than repairs: bad input (partial framing, moving camera) is the largest source of failure in the documented issues.

### Gaps
- No measured GEM-X or GVHMR end-to-end seconds-per-clip on this GPU; must be measured in the PoC.
- The estimate for the GEM-X-to-Kimodo glue is the least certain number in this note because no document shows the conversion.
- Licence and commercial-use constraints (SMPL, GEM-X weights, GVHMR, hand models) are out of scope here (another researcher); they gate which route is acceptable for a game the owner may sell.

## 7. Face (optional)

### Takeaway
The lowest-effort face route is MetaHuman Animator from mono video (UE 5.6+) or the new markerless plugin (body+face from one camera); MediaPipe Face Landmarker gives 52 blendshape scores for a lightweight open alternative; FLAME-based trackers like SMIRK carry old torch/pytorch3d pins and FLAME-registration caveats.

### Cited Findings
- **MetaHuman Animator mono video**: UE 5.6 or later with the MetaHuman Animator plugin; offline workflow sets Input Type to Monocular Footage on a MetaHuman Performance asset, selects the ingested mono-video CaptureData and clicks Process; footage can come from a mono camera or Live Link Face using a non-TrueDepth camera; 5.8 release notes add offline and real-time facial functionality on Linux and macOS. VERIFIED (via search summaries of Epic docs; the doc page itself returned only its title in my fetch). [Epic: animation from mono video](https://dev.epicgames.com/documentation/metahuman/animation-from-mono-video), [MetaHuman 5.8 release notes](https://dev.epicgames.com/documentation/metahuman/metahuman-5-8-release-notes-in-unreal-engine)
- **Epic markerless plugin** (UE 5.8+, Windows, experimental) can solve body and face from the same single-camera video or pair face footage from a separate camera, with output assigned to a MetaHuman in a level sequence. VERIFIED. [Digital Production](https://digitalproduction.com/2026/06/23/metahuman-gets-markerless-mocap/)
- **MediaPipe Face Landmarker**: outputs 52 facial blendshape scores when `outputFaceBlendshapes` is enabled (off by default), and a 4x4 facial transformation matrix; supports a VIDEO running mode that processes every frame with monotonic timestamps; Python via `pip install mediapipe`; model licence is on a linked model card (not read). VERIFIED. [MediaPipe Face Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)
- **SMIRK** (3D face reconstruction from images): repo lists an MIT licence but needs FLAME registration, PyTorch3D, Python 3.9 with CUDA 11.7 in the suggested setup, and a bash `quick_install.sh`; no Windows notes. VERIFIED. [SMIRK README](https://github.com/georgeretsi/smirk)
- GEM-X's README (per search summary) describes full-body 77-joint motion including body, hands and face; SOMA's 77 joints include face joints (ProtoMotions drops them as "leaf end-effectors without actuators"). VERIFIED (summary/secondary). [GEM-X search result](https://github.com/NVlabs/GEM-X), [ProtoMotions SEED BVH preparation](https://nvlabs.github.io/ProtoMotions/getting_started/seed_bvh_preparation.html)

### Inferences
- Face and body should be solved as separate streams and merged in Sequencer or by combining the face curves with the body animation, since the body pipeline above does not produce MetaHuman face curves.
- MediaPipe's 52 scores are ARKit-style names; mapping them onto MetaHuman face curves is plausible but I did not verify the mapping or the resulting quality (UNVERIFIED). MetaHuman Animator's own mono solve is likely higher quality and is the one that is engine-native.
- SMIRK-class trackers (old torch/CUDA pins, pytorch3d) would cost the same Windows/Blackwell friction as the body models and are not worth it for a first pass.

### Gaps
- EMOCA and LivePortrait were not researched; licence caveats (FLAME, non-commercial datasets) for any FLAME-based tracker were not verified.
- No quality comparison of MetaHuman Animator mono video vs MediaPipe vs the markerless plugin was found.
- Eye and head-pose handling for the body pipeline were not researched.
