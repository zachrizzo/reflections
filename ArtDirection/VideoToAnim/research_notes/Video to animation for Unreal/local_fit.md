## 1. The Kimodo plugin: where it lives, what it produces, how it bakes

### Takeaway
Kimodo is an Epic-shipped experimental ENGINE plugin (the project has no `Plugins\` folder) wrapping NVIDIA's Kimodo text-to-motion diffusion model, pinned to `nvidia/Kimodo-SOMA-RP-v1.1`. It outputs 30 fps motion on a 31-bone SOMA skeleton (synthetic `root` + 30 joints, no fingers), Y-up metres converted to UE centimetres. It has no BVH/NPZ/FBX import or export: its only inputs are text, pose/effector/trajectory constraints from Sequencer, and its only UE outputs are generated sections that are baked to an AnimSequence through the AnimGenOffline/AnimMixer path in the live editor.

### Inferences
- Kimodo is a generative text/constraint-to-motion model, not a video-to-motion estimator; nothing in it ingests video. A video pipeline can only (a) produce its own AnimSequence/FBX on another skeleton and retarget (Q2), or (b) feed Kimodo as constraints: keyed full-body target poses, hand/foot/hips pins and a root trajectory (the Imported Trajectory generator reads a root track from an AnimSequence) with text, letting the model fill and clean the motion. (b) is a design option, not something tested here.
- The shared-memory worker protocol and the generator registry make a custom video-to-motion "generator" technically possible, but only through a new C++ editor module in `Source/`, which the build-train rules (Q4) make costly.
- A SOMA-native video estimator would be a clean fit (31 bones, same rest convention); its output would need the plugin's "standard T-pose rebased to BONES-SEED rest" convention or an explicit retarget, since there is no BVH reader here.
- Today's assets (`Content/Animation/`) are untracked in git (`?? Content/Animation/`), so they are not backed up by the repo yet. — [Source](cmd://git-status)

## 2. SOMA to MetaHuman retargeting: what exists, what could consume a video pipeline's output

The skill is at `C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/SKILL.md` (there is NO `blender-to-unreal` folder under `AppData/Roaming/Claude`; the older marketplace copy at `.claude/plugins/marketplaces/zachrizzo-marketplace/plugins/blender-to-unreal/` lacks the fps/same-skeleton/Error-32 rules, so use the cache version). Its rule: measure an existing sibling asset and match its convention when joining an existing skeleton; the locked export settings are for assets you own end to end.

### Cited Findings (checklist)
- **One rig, one pass.** Export mesh and every action from the single armature the mesh is skinned to; different armature object names become different UE skeletons. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/SKILL.md>)
- **Armature object name.** Project rule: name the rig object exactly `root` (not `Armature`, not `Rig_X`) before `export_scene.fbx`, moving any other object called `root` aside; `Armature` drops the root bone (leaving `pelvis` as bone 0), any other name becomes a foreign root that REPLACES the skeleton's `root`; restore names afterwards. After import check bone 0 and the 342-bone count. — [Source](<C:/Users/zachc/.claude/projects/C--Users-zachc-Documents-Unreal-Projects-reflections/memory/blender-armature-name-ue-skeleton.md>)
- **Scale/units.** Blender scene unit scale 1 (metres); export `apply_unit_scale=True`, `apply_scale_options='FBX_SCALE_NONE'`, `global_scale=1.0`, `bake_space_transform=False`; import `import_uniform_scale=1.0`, `convert_scene=True`, `convert_scene_unit=True`. Verify a 1.67 m mesh imports at about 167 cm. `import_uniform_scale=0.01` is only for legacy ×100 skeletons (read the value from the project's existing import script, per skeleton). — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/gotchas.md>)
- **Axes.** `axis_forward='-Z'`, `axis_up='Y'`, `primary_bone_axis='Y'`, `secondary_bone_axis='X'`; UE forward is +X; confirm the front with one render and normalise at the source (rig +90° about Z in the skill's convention), never patch with a Blueprint/component yaw. Other locked flags: `add_leaf_bones=False`, `mesh_smooth_type='FACE'`, `use_armature_deform_only=False`, `path_mode='COPY'`. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/pipeline-scripts.md>)
- **Animation export.** Mesh FBX `bake_anim=False`; each clip FBX `bake_anim=True`, `bake_anim_use_all_bones=True`, `bake_anim_force_startend_keying=True`, `bake_anim_use_all_actions=False`, `bake_anim_use_nla_strips=False`, scene frame range set to the action's range; recentre the rig to the origin during export and restore after; for Blender 4.4+ slotted actions also set `animation_data.action_slot`. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/pipeline-scripts.md>)
- **Frame rate.** `export_scene.fbx` has no fps argument: it bakes at `scene.render.fps`. Set the scene fps to the target library's rate for the export (derive it from an untouched sibling: `n_frames / sequence_length`), restore it, and require `sequence_length ≈ n_frames/fps`. This is the only check that catches a 30-vs-24 mismatch. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/SKILL.md>)
- **Animation import settings (UE).** `AssetImportTask(automated=True, replace_existing=True, replace_existing_settings=True, save=True)`; `FbxImportUI(import_mesh=False, import_animations=True, skeleton=<existing skeleton>, mesh_type_to_import=FBXIT_ANIMATION)`; `anim_sequence_import_data`: `import_uniform_scale=1.0`, `convert_scene=True`, `convert_scene_unit=True`, `remove_redundant_keys=False`. Shared skeleton: pass the EXISTING skeleton so the new clip inherits it; for a new character reuse an identical skeleton. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/pipeline-scripts.md>)
- **Per-clip gates.** (1) strip the animated armature-object bone track with `remove_bone_animation(..., include_children=False)` (`True` wipes the clip); (2) track count equals an untouched clip on the same skeleton; (3) `root` yaw equals that sibling's (two skeletons can hold facing in different bones, which makes the unit walk sideways); (4) length/fps check; (5) saved write landed (`save_asset` result / file mtime); (6) no per-bone displacement fling; (7) metrics validated against a known-good control; compare left/right in component space; (8) visual confirmation. — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/pipeline-scripts.md>)
- **Process.** Blender must be OPEN with its MCP; import headless and automated with the editor CLOSED (the skill's recipe: `UnrealEditor-Cmd.exe "<uproject>" -ExecutePythonScript="<file.py>" -unattended -nopause -nosplash -NoLiveCoding -stdout`). — [Source](<C:/Users/zachc/.claude/plugins/cache/zachrizzo-marketplace/blender-to-unreal/1.0.0/skills/blender-to-unreal/references/pipeline-scripts.md>)

### Inferences
- The skill's closed-editor rule conflicts with this repo's always-open shared editor; for a MetaHuman-skeleton animation import the safe combination is the skill's settings + the `root`-named armature rule + a throwaway-skeleton proof + live-editor or closed-editor import per Q4.

### Gaps
- The skill is written for character meshes + Blender actions; it has no BVH/SMPL-specific guidance (BVH import to Blender, rest-pose alignment) and none for MetaHuman correctives/twist bones (342-bone rig).
- I did not run any of its scripts.
