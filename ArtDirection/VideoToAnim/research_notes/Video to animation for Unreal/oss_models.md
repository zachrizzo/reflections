# Open-source SMPL-family and newer monocular-video human motion models (as of 2026-11-21), for a Windows RTX 5080 batch pipeline

Method note: all facts below were read on GitHub (repo pages, raw README/LICENSE files, the GitHub REST API for pushed_at/stars/licence/issues), arXiv, Hugging Face or project pages on 2026-11-21. The fetch tool returns a model-written summary of each page, so quoted licence sentences should be re-read on the linked page before any legal reliance. "VERIFIED" = read on a primary source via the cited URL (no further tag means VERIFIED). "UNVERIFIED" = secondary, snippet-only or inferred. Not legal advice. GitHub `pushed_at` = last commit push. The scope split: NVIDIA GEM-X/SOMA/Kimodo, Meta SAM 3D Body/MHR and SMPL/Meshcapade licence details are covered by another researcher; they appear here only where they are dependencies of the models I cover.

## 1. Which models are best now, and what newer models exist (2025-2026)?

### Takeaway
The strongest practical open candidates in Nov 2026 are the GVHMR family (GVHMR, and its Oct 2026 derivative ExMR which adds fingers/feet), the brand-new FlowHMR (Oct 2026, best overall quality in one Windows-app maintainer's subjective tests but slow and heavy), and PromptHMR-Video (best published EMDB-2 numbers of the classic models, multi-person). All three are explicitly non-commercial in code or weights. The older MIT/Apache-code models (WHAM, TRAM, 4DHumans, SAT-HMR, MotionBERT) are weaker or stale and still depend on non-commercial body models and datasets.

### Cited Findings
- GVHMR (SIGGRAPH Asia 2024) EMDB-2 world metrics: WA-MPJPE100 111.0 mm, W-MPJPE100 276.5 mm, RTE 2.0 %, jitter 16.7, foot-sliding 3.5; RICH: 78.8 / 126.3 / 2.4 / 12.8 / 3.0. WHAM on the same table: EMDB 135.6 / 354.8 / 6.0 / 22.5 / 4.4. [GVHMR paper](https://arxiv.org/html/2409.06662)
- PromptHMR paper's world-grounded EMDB-2 table (24 joints): WHAM 135.6/354.8/6.0/22.5/4.4; TRAM 76.4/222.4/1.4/18.5/23.4; GVHMR 111.0/276.5/2.0/16.7/3.5; PromptHMR-Vid 71.0/216.5/1.3/16.3/3.5 (columns WA-MPJPE100, W-MPJPE100, RTE %, jitter, foot skating). Authors say PromptHMR-Vid beats TRAM on foot skating because it estimates joint contact probabilities. [PromptHMR paper](https://arxiv.org/html/2504.06397)
- TRAM's own paper reports EMDB-2: TRAM 76.4 / 222.4 / 1.4 % vs WHAM(DROID) 133.3 / 343.9 / 4.6 %, SLAHMR 326.9 / 776.1 / 10.2 %; it does not report jitter or foot sliding and lists foot sliding and penetration as unaddressed. [TRAM paper](https://arxiv.org/html/2403.17346)
- FlowHMR (arXiv 2610.03691, Oct 2026): flow-matching generative model (0.46 B-param MM-DiT) post-trained with GRPO using a physics-tracking reward; RICH: WA-MPJPE 56.68, W-MPJPE 88.43, PA-MPJPE 31.40, RTE 1.82 %, jitter 6.71, foot sliding 3.14 (the paper's re-run of GVHMR: 82.83 / 133.08 / 40.05 / 2.49 / 20.69 / 3.64). Physical-tracking success on Wild-4K: 82.47 % vs 62.82 % for GVHMR. The paper says DuoMo has lower WA-MPJPE, W-MPJPE and RTE than FlowHMR on RICH. These are the authors' own numbers. [FlowHMR paper](https://arxiv.org/html/2610.03691v1)
- Discrepancy to flag: the FlowHMR paper's GVHMR RICH numbers (82.83 / 133.08, jitter 20.69) differ from GVHMR's own paper (78.8 / 126.3, jitter 12.8) — different evaluation settings are likely, not confirmed. [FlowHMR paper](https://arxiv.org/html/2610.03691v1); [GVHMR paper](https://arxiv.org/html/2409.06662)
- A Windows-app maintainer's subjective ranking (RTX 5090 test PC; not an accuracy benchmark): FlowHMR "best overall motion quality" but slow; ExMR good quality and faster, default for new work; GVHMR lowest overall quality but sometimes better on unusual poses such as backflips; PromptHMR quality lower than ExMR but helps multi-person placement; GEM-X fast but lower quality. [RGB MoCap user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)
- ExMR (Wehrbein and Rosenhahn, arXiv 2610.26213, repo created 2026-10-20, last push 2026-10-30, 146 stars): temporal whole-body estimator plus FootMR/HandMR refinement; outputs SMPL-X body, hands, feet. The repo says it is a derivative work of GVHMR; it gives no benchmark numbers ("evaluation and training code ... will follow"). [ExMR repo](https://github.com/twehrbein/ExMR); [ExMR API](https://api.github.com/repos/twehrbein/ExMR); [RGB MoCap ExMR doc](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/models/EXMR.md)
- DuoMo (Meta, arXiv 2603.03265, CVPR 2026): two diffusion models (camera-space then world-space lift/refine); outputs 595 raw vertices (LOD6 of Meta's Momentum Human Rig), not SMPL parameters; claims 16 % lower world-space MPJPE on EMDB and 30 % on RICH vs prior work. Repo github.com/facebookresearch/DuoMo exists (last push 2026-07-17, 74 stars, licence "Other"/no SPDX); the project page does not mention released weights or a licence. [DuoMo project page](https://yufu-wang.github.io/duomo); [DuoMo repo API](https://api.github.com/repos/facebookresearch/DuoMo)
- Human3R (ICLR 2026, arXiv 2510.06219): one-stage online model giving global multi-person SMPL-X, dense scene and camera trajectory; about 15 FPS and about 8 GB; one-day single-GPU training on BEDLAM; built on CUT3R. [Human3R arXiv](https://arxiv.org/abs/2510.06219)
- PEAR (IDEA, SIGGRAPH 2026, arXiv 2601.22693): real-time (claims 100 FPS) expressive mesh recovery (EHM-s parameters), image-level; repo Apache-2.0, created 2026-02-02, last push 2026-09-22; needs SMPL, SMPL-X, FLAME assets; training data not released. In RGB MoCap it is only a one-person live preview with no recording/export. [PEAR README](https://api.github.com/repos/Pixel-Talk/PEAR/readme); [PEAR repo API](https://api.github.com/repos/Pixel-Talk/PEAR); [RGB MoCap PEAR doc](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/models/PEAR.md)
- HTD-Refine (arXiv 2605.26879) is a plug-in refiner for GVHMR/TRAM output; the app's notices list it as AGPL-3.0-only. [search result, snippet only; UNVERIFIED benchmark detail](https://arxiv.org/html/2605.26879); [RGB MoCap third-party notices](https://raw.githubusercontent.com/toyxyz/toyxyz_RGBMocap/main/THIRD_PARTY_NOTICES.md)
- GENMO was renamed GEM (Dec 2025); GEM-SMPL checkpoint released March 2026 on Hugging Face `nvidia/GEM-X`. [GENMO/GEM README](https://raw.githubusercontent.com/NVlabs/GENMO/main/README.md)
- Mocap-2-to-3 (CVPR 2026) reportedly beats GVHMR+SMPLify; I only saw a search snippet. UNVERIFIED. [search result](https://arxiv.org/pdf/2503.03222)
- Found no independent head-to-head benchmark of GVHMR vs PromptHMR vs FlowHMR vs ExMR on the same clips; the quality ranking rests on the authors' papers plus one app maintainer's notes. [RGB MoCap user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)

### Inferences
- "Best now" for quality is FlowHMR or ExMR (both by weak evidence), for published numbers PromptHMR-Video, for proven Windows install GVHMR. None of them can be shipped commercially without separate permission (see section 2).
- Paper-vs-paper numbers are not directly comparable (different GPU/seeds/joint sets/post-processing).

### Gaps
- No independent benchmark; no RTX 5080-specific timings for any model (the only app timings are from an RTX 5090 32 GB).
- DuoMo licence and weights availability not confirmed.

## 2. LICENCES and whether OUTPUT motion could ship in a commercially sold game

### Takeaway
Every model with strong published world-grounded quality carries an explicit non-commercial restriction on code and/or weights (GVHMR, ExMR, PromptHMR, FlowHMR weights, GEM, Multi-HMR, Human3R, SMPLest-X, TokenHMR, CoMotion). The MIT/Apache-code models (WHAM, TRAM, 4DHumans, SAT-HMR, MotionBERT) still need the SMPL body model and were trained on non-commercial datasets (AMASS, BEDLAM, H36M etc.), so their commercial status is unresolved, not cleared. No licence I read says who owns the output motion; the practical risk is lack of permission to run the software/weights for commercial purposes.

Could the OUTPUT motion ship in a commercially sold game?
- GVHMR, ExMR, PromptHMR, FlowHMR (weights), GEM, CoMotion, Multi-HMR, Human3R, SMPLest-X/SMPLer-X, TokenHMR, CameraHMR, WiLoR, EMOCA: NO without a separate commercial licence. The licences read do not claim ownership of outputs. Commercial routes named in the sources: ZJU authors (GVHMR), Meshcapade (PromptHMR), MPI (ps-license@tue.mpg.de for TokenHMR, EMOCA, AMASS; smpl@max-planck-innovation.de for BEDLAM). - MotionBERT/MotionAGFormer: Apache-2.0 code, no SMPL, but H36M-trained and output has no joint rotations or global path; cleaner on paper, not cleared (H36M terms unread).

### Inferences
- The "output is just numbers" argument is untested; none of the licences I read says outputs are free of the licence. Prudent reading: if the pipeline is part of producing a sold product, the tool itself must be licensed for commercial use.
- Within SMPL-world-grounded models, TRAM (MIT code, no weights restriction stated) and WHAM (MIT, AMASS-trained) are the least encumbered on paper, but still depend on SMPL and unlicensed-for-commercial datasets.

### Gaps
- Did not read the SMPL/SMPL-X/MANO/FLAME licence texts (assigned to another researcher), H36M terms, or the HMR2/TRAM/WHAM training-data lists in full.
- Did not confirm OSX weights terms or whether Multi-HMR's Anny checkpoint has its own licence file.
- No lawyer-grade statement on whether outputs inherit training-data licences.

## 3. Output type, world-space translation, moving camera, contacts, hands and face

### Takeaway
GVHMR, WHAM, TRAM, PromptHMR-Video, GEM, Human3R and FlowHMR give world/gravity-aligned motion from video; 4DHumans, CameraHMR, TokenHMR, CoMotion, Multi-HMR, SAT-HMR, SMPLest-X and the lifting models are camera-space or per-frame only. Only the SMPL-X models derived from or wrapped around hand estimators give fingers (ExMR, SMPLest-X, Multi-HMR, FlowHMR via SMPL-H); GVHMR and PromptHMR give no fingers.

### Cited Findings
- **GVHMR**: predicts SMPL-X parameters; world frame is "gravity-view"; camera rotation from visual odometry; DPVO no longer default since 2025-03-08, replaced by SimpleVO; `-s` flag skips VO for static cameras. [README](https://raw.githubusercontent.com/zju3dv/GVHMR/main/README.md); [INSTALL.md](https://raw.githubusercontent.com/zju3dv/GVHMR/main/docs/INSTALL.md). Network predicts stationary probabilities for hands, toes and heels, uses them to update global translation and a CCD IK solver to reduce foot sliding; preprocessing uses relative camera rotation only (DPVO or gyro). [GVHMR paper](https://arxiv.org/html/2409.06662). Does not estimate fingers (issue #10; feature request #85 open since Dec 2025). [issue #10](https://github.com/zju3dv/GVHMR/issues/10); [issue search](https://api.github.com/search/issues?q=repo:zju3dv/GVHMR+(lying+OR+crawl+OR+sitting+OR+floor+OR+jitter+OR+foot)&per_page=20)
- **WHAM**: world-grounded SMPL; uses DPVO or DROID-SLAM for camera motion; `--estimate_local_only` skips SLAM for camera-coordinate motion; `--run_smplify` optional temporal refinement; `--calib` known intrinsics. [README](https://raw.githubusercontent.com/yohanshin/WHAM/main/README.md). Foot-contact output: not stated in the README (UNVERIFIED).
- **TRAM**: masked DROID-SLAM for camera motion, background used for metric scale (ZoeDepth credited for metric depth), VIMO video transformer for body; `--static_camera` flag; "better gravity & floor prediction" in Feb 2025 update. Moving camera handled; SLAM needs known focal length. [README](https://raw.githubusercontent.com/yufu-wang/tram/main/README.md); [TRAM abstract](https://arxiv.org/abs/2403.17346); [TRAM paper](https://arxiv.org/html/2403.17346)
- **CameraHMR**: per-image SMPL regression with predicted full-perspective camera (HumanFoV); demo processes an image folder; no video/tracking in README. [README](https://github.com/pixelite1201/CameraHMR); [project page](https://camerahmr.is.tue.mpg.de/)
- **4DHumans/HMR2.0**: per-frame SMPL plus PHALP tracking; output a .pkl with 3D pose and shape per tracklet and .obj meshes; camera-space (README describes no world output). [README](https://raw.githubusercontent.com/shubham-goel/4D-Humans/main/README.md)
- **TokenHMR**: CVPR 2024 image model (tokenized pose); no video/world output described. Repo description only. [API](https://api.github.com/repos/saidwivedi/TokenHMR)
- **PromptHMR / PromptHMR-Video**: SMPL-X (README does not name it explicitly); moving camera via DROID-SLAM + ZoeDepth (paper); contact joints optimized to zero velocity; multi-person world-coordinate video; `--static_camera` flag; outputs `results.pkl`, a GLB and an MCS file; no finger output in the Windows app. [README](https://github.com/yufu-wang/PromptHMR); [paper](https://arxiv.org/html/2504.06397); [app guide](https://github.com/toyxyz/toyxyz_RGBMocap)
- **CoMotion**: online multi-person tracking from a monocular stream; saves SMPL pose parameters as .pt; README does not say whether poses are global or camera-space and does not address a moving camera. [README](https://github.com/apple/ml-comotion); [abstract](https://arxiv.org/abs/2504.12186)
- **GENMO/GEM-SMPL**: video, 2D keypoints, text, audio; `smpl_params.pt` holds both global and in-camera body parameters; hands and face are in the separate GEM-X project. [README](https://raw.githubusercontent.com/NVlabs/GENMO/main/README.md)
- **SMPLest-X / SMPLer-X / OSX / Multi-HMR**: SMPL-X whole-body (body, hands, face) per frame, camera-space; SMPLest-X and SMPLer-X have video-file inference scripts that process frames independently (no world trajectory described); Multi-HMR demo takes an image folder, runtime on V100: ViT-L 896 = 126 ms, ViT-L 672 = 74 ms, ViT-B 672 = 43 ms, ViT-S 672 = 29 ms. [SMPLest-X](https://raw.githubusercontent.com/SMPLCap/SMPLest-X/main/README.md); [SMPLer-X](https://raw.githubusercontent.com/caizhongang/SMPLer-X/main/README.md); [Multi-HMR](https://github.com/naver/multi-hmr)
- **SAT-HMR**: multi-person image mesh estimation; no video support mentioned. [README](https://github.com/ChiSu001/SAT-HMR)
- **Human3R**: global multi-person SMPL-X + scene + camera from video in one pass. [arXiv](https://arxiv.org/abs/2510.06219)
- **FlowHMR**: SMPL-H (hands encoded), camera rotations from VGGT-Omega as conditioning, one motion per video; saves .npz and optional .fbx; multi-person via a person picker in the web demo. [paper](https://arxiv.org/html/2610.03691v1); [repo](https://github.com/flowhmr/flowhmr)
- **ExMR**: SMPL-X body, hands and feet; outputs camera and gravity-aligned world frames; camera rotation from SimpleVO track, displacement estimated from body-root predictions; optional "Refine Camera Rotation" (up to 2 degrees); default is Static Camera. [ExMR repo](https://github.com/twehrbein/ExMR); [RGB MoCap ExMR doc](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/models/EXMR.md)
- **MotionBERT / MotionAGFormer**: take 17-joint H36M-format 2D keypoints and lift to 3D (MotionBERT up to 243 frames per input); MotionAGFormer demo needs YOLOv3 + HRNet for 2D. Output joint positions; no SMPL mesh/rotations stated; global trajectory not stated (UNVERIFIED, root-relative is the usual convention for these lifters). [MotionBERT](https://github.com/Walter0807/MotionBERT); [MotionAGFormer](https://github.com/TaatiTeam/MotionAGFormer)
- **NLF** (extra, NeurIPS 2024): weights "available for noncommercial research use"; code licence not stated in README (GitHub says MIT). [README](https://raw.githubusercontent.com/isarandi/nlf/main/README.md); [API](https://api.github.com/repos/isarandi/nlf)

### Inferences
- GVHMR/ExMR use only relative camera rotation, so camera translation (dolly, walking handheld) is absorbed into body-root estimates; TRAM/PromptHMR use SLAM+metric depth and should handle translating cameras better. This follows from the preprocessing descriptions above, not from a direct test.
- For Unreal retargeting from SMPL-X the finger channels would otherwise come from a hand model (section 9).

### Gaps
- WHAM foot-contact details and CoMotion world-space behaviour not stated in READMEs.
- Whether MotionBERT/MotionAGFormer can output global translation: not found.

## 4. Quality: benchmarks and honest failure modes

### Takeaway
Published world-grounded numbers: PromptHMR-Video (71.0 WA-MPJPE EMDB-2) and TRAM (76.4) lead the classic models, GVHMR (111.0) has far less foot-skating than TRAM (3.5 vs 23.4), WHAM is clearly behind (135.6). FlowHMR/DuoMo/ExMR claim better but are weeks-to-months old with author-reported numbers only. Documented failure modes are mostly foot sliding, wrong feet, depth/contact errors, identity swaps and occlusion; I found no sourced reports on loose clothing or lying/crawling.

### Cited Findings
- EMDB-2 / RICH numbers as in section 1. [GVHMR paper](https://arxiv.org/html/2409.06662); [PromptHMR paper](https://arxiv.org/html/2504.06397); [TRAM paper](https://arxiv.org/html/2403.17346)
- TRAM VIMO on 3DPW camera-space: PA-MPJPE 35.6 mm, MPJPE 59.3 mm, PVE 69.6 mm. [TRAM paper](https://arxiv.org/html/2403.17346)
- GVHMR 3DPW PA-MPJPE is 0.3 mm behind WHAM, which the authors tentatively attribute to predicting SMPL-X; internet-video results in the paper are qualitative only. [GVHMR paper](https://arxiv.org/html/2409.06662)
- WHAM "fails when the motion is outside the MoCap data" (walking down stairs, skateboarding) per the TRAM authors. [TRAM paper](https://arxiv.org/html/2403.17346)
- GVHMR user reports: very noticeable foot sliding (#21); wrong foot pose because feet are not detected keypoints (#35); translation jitter where two separately processed 4-second clips are joined (#34); overlay scale/pose problems on some inputs (#68); heavy sliding when forcing a known XYZ position (#64); multi-person alignment needs custom scripts (#30, #10). [issue search](https://api.github.com/search/issues?q=repo:zju3dv/GVHMR+(lying+OR+crawl+OR+sitting+OR+floor+OR+jitter+OR+foot)&per_page=20); [issue #10 comments](https://api.github.com/repos/zju3dv/GVHMR/issues/10/comments?per_page=30)
- Windows-app maintainer notes: multi-person tracking without "Find person" picks one person and may swap identities; contact detection is an estimate and can leave sliding or penetration; hanging poses and object interaction are better fixed in a 3D editor; FlowHMR limited to 5,000 frames per take; PromptHMR contacts and depth can still be wrong; ExMR failures: occlusion, motion blur, poor visibility, identity changes. [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md); [ExMR doc](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/models/EXMR.md)
- FlowHMR limitations: only ground-plane physical tests; object and support-surface interactions not modelled. [paper](https://arxiv.org/html/2610.03691v1)
- PromptHMR: monocular regression cannot avoid interpenetration between closely interacting people; shape/interaction prompts must be supplied by the user. [paper](https://arxiv.org/html/2504.06397)

### Inferences
- For single-person everyday motion on a mostly static or gently moving camera, GVHMR-class quality is adequate but foot contact needs cleanup (ExMR's FootMR and the app's Contact Correction target exactly this).

### Gaps
- No sourced failure reports on loose clothing, lying/crawling/floor poses, cropped bodies, or fast motion for any model (searched GVHMR issues; none matched).
- No quantitative numbers for ExMR, WHAM foot-contact, or Human3R on EMDB/RICH found.

## 5. Speed, VRAM and preprocessing

### Takeaway
GVHMR is light (about 5 GiB peak VRAM, network 0.28 s for 1430 frames on an RTX 4090) with preprocessing dominating the runtime; ExMR about 11 GiB peak (3.9 GiB in low-memory mode); FlowHMR is the heaviest (10.7-14.9 GiB peak on a 32 GB card, minutes per clip). A 16 GB RTX 5080 should fit GVHMR/ExMR/PromptHMR; FlowHMR is tight without Low Memory mode.

### Cited Findings

## 6. Windows, RTX 50-series / CUDA 12.8 / cu128 status and install pain

### Takeaway
Only GVHMR (and wrappers around GVHMR, ExMR, FlowHMR, PromptHMR) has verified native Windows + Blackwell evidence, via a community port (torch 2.7.1+cu128, CPU-only pytorch3d, SimpleVO instead of DPVO) and the RGB MoCap app (tested on RTX 5090). For WHAM/TRAM, DPVO/DROID-SLAM CUDA extensions are the Windows and sm_120 pain point; 4DHumans needs detectron2 (hard on Windows) or a YOLO swap. Upstream pins are cu118/cu121 (Blackwell-incompatible) for most repos.

### Cited Findings
- Blackwell needs torch 2.7.0+ with cu128: upstream GVHMR pins torch 2.3.0+cu121 which cannot run on sm_120; a community port runs GVHMR on native Windows 11 with an RTX 5060 Laptop (sm_120) on torch 2.7.1+cu128, python 3.10, MSVC 14.44; pytorch3d 0.7.9 built CPU-only from source (no Windows wheel), checkpoints (about 5.2 GB) from a Hugging Face mirror because Google Drive is rate-limited; `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` fixes about 40 `torch.load` call sites after torch 2.6's default change; DPVO not installed, SimpleVO used; setuptools 84 broke MSVC flag passing, fixed through the `CL` environment variable. [PS12007 port](https://github.com/PS12007/video-to-humanoid-mimicry)
- GVHMR issue #77 (RTX 5060, open): sm_120 error; reported fix is CUDA 12.8 plus PyTorch 2.7 (comment says "2.70"), with a numpy version conflict mid-install (uninstall numpy or install requirements last). [issue #77 comments](https://api.github.com/repos/zju3dv/GVHMR/issues/77/comments)
- GVHMR issue #23 (Windows): DPVO build fails with "unsupported Microsoft Visual Studio version" on VS2022 + CUDA 12.1; community notes say pytorch3d must be compiled and worked with VS2019 but not VS2022 (contradicts the PS12007 port, which used MSVC 14.44/VS2022 for a CPU-only build); a Nov 2025 user hit `ImportError: cannot import name 'DiagnosticOptions' from 'torch.onnx._internal.exporter'` (torch/lightning mismatch); issue #27 "How to install PyTorch3D on Windows 11" open; issue #6 closed. [issue #23 comments](https://api.github.com/repos/zju3dv/GVHMR/issues/23/comments); [issue search](https://api.github.com/search/issues?q=repo:zju3dv/GVHMR+windows&per_page=15)

Only ExMR and FlowHMR ship FBX/BVH themselves (ExMR: AMASS SMPL-X file, BVH, FBX for Unity/Unreal; FlowHMR: optional FBX). GVHMR, WHAM and TRAM have no official export; the community fills the gap, notably the RGB MoCap Windows app (FBX/BVH/VMD, UE5 Manny/Quinn FBX, Live Link).

### Cited Findings
- ExMR exports SMPL-X params in camera and gravity-aligned world frames (`results.pt`/`.npz`), an AMASS SMPL-X file for Blender, Unity/Unreal via FBX, robot retargeting, and a BVH skeleton. [ExMR repo](https://github.com/twehrbein/ExMR)
- FlowHMR saves `.npz`, plus `.fbx` if FBX export is installed. [FlowHMR repo](https://github.com/flowhmr/flowhmr)
- PromptHMR saves MCS (Meshcapade editor) and GLB (importable into Blender) plus `results.pkl`. [README](https://github.com/yufu-wang/PromptHMR)
- GVHMR: README mentions no Blender/FBX/BVH export; users import the result via a community "CEB 4d humans" Blender add-on that retargets to rigs such as Mixamo, or load SMPL/SMPL-X directly; the author of that add-on also shared multi-person scripts; imported SMPL-X vs SMPL mismatch is minor since GVHMR has no fingers. [README](https://raw.githubusercontent.com/zju3dv/GVHMR/main/README.md); [issue #10 comments](https://api.github.com/repos/zju3dv/GVHMR/issues/10/comments?per_page=30)
- WHAM: README mentions no export; a community script imports WHAM .pkl into Blender (issue #52; needs `joblib` installed in Blender). [issue search](https://api.github.com/search/issues?q=repo:yohanshin/WHAM+(commercial+OR+license+OR+windows+OR+5090+OR+5080)&per_page=20)
- TRAM: README mentions no Blender export; issue #3 asks for PKL export (open). [TRAM README](https://raw.githubusercontent.com/yufu-wang/tram/main/README.md); [issue search](https://api.github.com/search/issues?q=repo:yufu-wang/tram+(windows+OR+5090+OR+5080+OR+sm_120+OR+cu128+OR+install)&per_page=20)
- 4DHumans: exports `.obj` meshes and a `.pkl` of SMPL per tracklet; no rig export. [README](https://raw.githubusercontent.com/shubham-goel/4D-Humans/main/README.md)
- RGB MoCap (MIT app): FBX and BVH (Generic/Blender or 3ds Max Biped), VMD, character FBX, portable Blender projects, UE5 Manny/Quinn FBX, live streaming to Blender and Unreal Live Link, face coefficients as TXT or Unreal Live Link Face CSV; retargets to Mixamo FBX, VRM and PMX; Contact Correction with Flat Ground or Multi Level modes and timeline editing of foot/hand lock intervals. The page does not say how its retargeter works. [RGB MoCap](https://github.com/toyxyz/toyxyz_RGBMocap); [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)
- GEM-SMPL, CoMotion: outputs are `.pt` parameter files; no rig export in READMEs. [GENMO README](https://raw.githubusercontent.com/NVlabs/GENMO/main/README.md); [CoMotion README](https://github.com/apple/ml-comotion)

### Inferences
- For a MetaHuman target, the practical path is SMPL-X parameters (npz/pt or AMASS file) to Blender or direct retarget; a custom retarget on bone rotations from SMPL-X's 22 body joints is the part no repo solves for MetaHuman. The Windows app's UE5 Manny/Quinn export is the nearest ready-made UE route.

### Gaps
- Did not inspect RGB MoCap's retarget code or the quality of its Manny/Quinn output.

## 9. Hand and face options if the body model lacks them

### Takeaway
For fingers: HaMeR (MIT code, MANO non-commercial) or WiLoR (CC BY-NC-ND models); both are image-level and need a stage that merges hand rotations onto the body. For face: MediaPipe Face Landmarker is the only one with a permissive repo licence and a built-in blendshape output; SMIRK and EMOCA need FLAME (non-commercial). ExMR/SMPLest-X already include hands.

### Cited Findings
- HaMeR: image-folder demo, Python 3.10, needs MANO right-hand model via registration; README says predicted hand parameters were integrated into SMPL-X; video support not stated. [README](https://raw.githubusercontent.com/geopavlakos/hamer/main/README.md); [API](https://api.github.com/repos/geopavlakos/hamer)
- WiLoR: "WiLoR models fall under the CC-BY-NC--ND License"; `--fast` gives up to 1.6x faster inference with about 0.05 mm MPJPE loss; image-folder demo; MANO licence applies; LICENSE text is CC BY-NC-ND 4.0, which bars sharing adapted material. [WiLoR README](https://github.com/rolpotamias/WiLoR); [license.txt](https://raw.githubusercontent.com/rolpotamias/WiLoR/main/license.txt)
- GVHMR has an optional "HandFlow" add-on for hands in the Windows app (HaMeR-derived, MIT source per notices); the app also uses optional HaMeR for fingers and ExMR already includes HaMeR hand estimation. [RGB MoCap](https://github.com/toyxyz/toyxyz_RGBMocap); [third-party notices](https://raw.githubusercontent.com/toyxyz/toyxyz_RGBMocap/main/THIRD_PARTY_NOTICES.md); [ExMR doc](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/models/EXMR.md)
- SMIRK: monocular 3D face reconstruction (images; `demo_video.py` for video), code MIT, FLAME registration required, Python 3.9 / CUDA 11.7 / PyTorch3D; no ARKit blendshape mapping mentioned. [SMIRK](https://github.com/georgeretsi/smirk)
- EMOCA: non-commercial research licence, training for commercial use prohibited; last push Dec 2024. [LICENSE](https://raw.githubusercontent.com/radekd91/emoca/master/LICENSE)
- MediaPipe Face Landmarker: 478 3D landmarks, 52 blendshape scores (e.g. jawOpen, browDownLeft), optional 4x4 facial transformation matrix, VIDEO and LIVE_STREAM modes, `pip install mediapipe`; repo Apache-2.0 (docs do not state the licence or ARKit-compatibility; Windows not specifically stated). [MediaPipe docs](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker); [MediaPipe API](https://api.github.com/repos/google-ai-edge/mediapipe)
- RGB MoCap exports face coefficients as TXT or Unreal Live Link Face CSV; face tracking runs on CPU. [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md); [RGB MoCap](https://github.com/toyxyz/toyxyz_RGBMocap)

### Inferences
- If licence cleanliness matters, MediaPipe (Apache-2.0 repo) is the only hand/face-adjacent option in this list whose repo licence is permissive; its model-asset terms were not read (UNVERIFIED).

### Gaps
- MANO and FLAME licence texts not read here; MediaPipe model-asset licence not confirmed; no quality comparison of hand add-ons in video.

## 10. Ranked shortlist for a Windows RTX 5080 batch pipeline (generic everyday body motion)

### Takeaway
(1) GVHMR / ExMR family, (2) FlowHMR, (3) PromptHMR-Video. All three are non-commercial as released, so using any of them in a sold product needs a licence or permission; none is licence-clean. Least licence-risky on paper: TRAM (MIT code), then WHAM; fully permissive code but poor fit: MotionBERT/MotionAGFormer.

### Cited Findings
1. **GVHMR (or its Oct 2026 derivative ExMR)** — Reason: only model with verified native-Windows Blackwell evidence (torch 2.7.1+cu128 on an RTX 5060 Laptop, GVHMR on RTX 5090 inside RGB MoCap), about 5 GiB VRAM, 2-3 min per 7-26 s clip on a 5090, gravity-aligned world motion, built-in foot-contact handling, strong EMDB/RICH numbers vs WHAM; ExMR adds fingers/feet, BVH/FBX/Unreal export and is rated "good and faster" by the app maintainer, though it is brand new (146 stars) and Linux-tested upstream. Main risk: non-commercial licence ("prohibited for commercial use", ExMR is a derivative of it), no finger output in plain GVHMR, foot sliding and wrong feet in user issues, preprocessing uses AGPL YOLOv8. Sources: [GVHMR LICENSE](https://raw.githubusercontent.com/zju3dv/GVHMR/main/LICENSE); [PS12007 port](https://github.com/PS12007/video-to-humanoid-mimicry); [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md); [ExMR repo](https://github.com/twehrbein/ExMR)
2. **FlowHMR** — Reason: best overall quality in the one practical comparison found and strongest published RICH numbers among the open-code models (WA-MPJPE 56.68, jitter 6.71), Apache-2.0 code, SMPL-H hands, FBX export. Main risks: weights are non-commercial, depends on gated SAM 3D Body and non-commercial VGGT-Omega, Linux-first upstream (works through RGB MoCap on Windows), slow (5-8 min per 15-26 s clip on a 5090), peak VRAM up to 14.9 GiB so use Low Memory mode on 16 GB, repo only about 2 months old with author-only benchmarks. Sources: [FlowHMR paper](https://arxiv.org/html/2610.03691v1); [HF model card](https://huggingface.co/fafsaf1/flowhmr-0.46B/raw/main/README.md); [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)
3. **PromptHMR-Video** — Reason: best published EMDB-2 numbers of the established models (71.0 / 216.5 / 1.3, foot skating 3.5), moving-camera support via DROID-SLAM + depth, multi-person, about 4.6 GiB VRAM, GLB/MCS output, and a stated commercial route through Meshcapade. Main risks: non-commercial licence by default, no fingers, app maintainer found overall quality below ExMR with contact/depth errors, needs native builds (VS 2022 + CUDA 12.8) for Windows, training code withheld. Sources: [PromptHMR paper](https://arxiv.org/html/2504.06397); [LICENSE](https://raw.githubusercontent.com/yufu-wang/PromptHMR/main/LICENSE); [user guide](https://github.com/toyxyz/toyxyz_RGBMocap/blob/main/docs/USER_GUIDE.md)

**Least licence-risky (on paper)**: TRAM — MIT code, no weights restriction stated in the README, best 2024 world-coordinate accuracy (76.4 WA-MPJPE). It is still not cleared: SMPL body model needed, VIMO training-data terms not read (UNVERIFIED, likely BEDLAM/3DPW-type research data), foot sliding is high (23.4), last push June 2025, and DROID-SLAM builds on Windows/sm_120 are unproven. Next: WHAM (MIT, AMASS-trained, unresolved VIBE/SMPL question, abandoned since Apr 2024). For fully permissive code with no SMPL dependency, MotionBERT/MotionAGFormer (Apache-2.0) exist but give root-relative joint positions without rotations or world trajectory. Sources: [TRAM LICENSE](https://raw.githubusercontent.com/yufu-wang/tram/main/LICENSE); [TRAM README](https://raw.githubusercontent.com/yufu-wang/tram/main/README.md); [WHAM issue #91](https://github.com/yohanshin/WHAM/issues/91); [MotionBERT](https://github.com/Walter0807/MotionBERT)

### Inferences
- If a commercial release is the goal, the realistic options are (a) buy/obtain a commercial licence from the owner (ZJU for GVHMR/ExMR, Meshcapade for PromptHMR, MPI for BEDLAM/AMASS-dependent weights), (b) use these models only for reference/previs and re-animate by hand or with a commercially licensed system, or (c) retrain a clean model on commercially licensed motion data. These are my judgement, not sourced advice.
- Expected practical pipeline on a 5080: GVHMR/ExMR (SimpleVO, static-camera flag when applicable) then contact correction, FBX/BVH export, then retarget to MetaHuman.

### Gaps
- No 5080 measurements for any shortlisted model; FlowHMR/ExMR are weeks old with no independent validation.
- Commercial licence availability and price not confirmed for any vendor except the contact addresses in the licence texts.
